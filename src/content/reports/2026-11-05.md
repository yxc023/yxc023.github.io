## 跨项目观察

1. **"显式状态机"从一个仓库的做法变成一类做法。** opencode 用 56 个合并 PR 把生命周期状态重写为显式状态机，并把规则写进 `packages/app/AGENTS.md`（#61718）；pi 的 p2 用 `origin` / `scope` 声明"谁可以调、在哪可以调"（commit 07c9e5b），本质是同一件事的另一面——**把隐式约束变成可声明、可查询的条款**。两边的落点都不是代码风格，而是"约束要能被检索到"。

2. **三家仓库同期在拆"先整体读入再切片"的模式。** pi 把 read 改成流式（#11750，200MB 日志读一行从 638MB 峰值降到只留显示行）、MCP 大消息改成线性分帧（#11791）；opencode 把 compaction 提前量从窗口百分比改成固定 token（#60049）、把 assistant part 逐行写入而不是重写整条消息（#58916）、给 MCP 加连接池（#61185）；hindsight 把 recall 路径上的 JIT 编译关掉（#6317）并砍掉 8 处"查询范围比需要的大"（#6323–#6330）。**共同的成本模型是"同一份工作只做一次"**。

3. **性能问题的性质在这批仓库里高度一致：范围过大，而非算法不足。** hindsight 那 8 个带量化指标的 issue 全部是"先全量统计再过滤"（1593×、778×、393×、317× 的改善全部来自把过滤提前）。opencode 的 compaction 与 MCP 池化是同一逻辑的应用侧版本。**这是数据规模问题，不是算法问题**——对应的修复都在"缩小作用域"而非"换实现"。

4. **模型能力的"声明 vs 实际"仍是最大的单点故障源。** opencode 侧 deepseek-v4.1-flash 声明支持图像却拒绝图像输入并卡死会话（#61827 / #61842）、gemini-4-argon 返回 403（#61845）；pi 侧 minimatch 的 advisory 让每个下游项目 `npm audit` 失败，只能跨 major 跳到 11.0.3（#11789）；hindsight 侧 reflect 在 MiniMax 上因 `strict json_schema` 含 nullable 报 400（#6321）。**上游的能力声明与下游的严格校验之间的缝隙，正在制造大量跨仓库的重复劳动。**

5. **"身份唯一性"取代"检索质量"成为记忆系统与多租户服务的新主线。** hindsight 修了 bank 别名接管（#6318——别名会让所有调用方静默读到副本）、restore 合并导致事实重复（#6335）、bank/alias/mental model 三套 id 规则（#6282）；opencode 修了 URL 凭据与 fragment 绕过 deny 规则（#61701）并加了 `websearch.use` 策略按 provider ID 封禁（#61557）。**边界一旦被多个调用方共享，身份唯一性就比单点性能更影响正确性。**

6. **供给侧的不稳定仍然每天产生新的用户报告。** opencode 的 Go 模型线新增 Hy4（#61709）的同时，Go 模型的图像能力与 403 问题在同一天出现（#61827 / #61845），免费额度类 issue（#61716 / #61782 / #61553 / #61599）反复出现，Linux 桌面端还有 renderer 100% CPU 的崩溃循环（#61688）；open issues 从 3990 涨到 4013。pi 一侧则用"同价或更低价换新模型"（d84123b）在成本侧对冲。

7. **社区贡献的重心从"提 issue"转向"提带 patch 的量化报告"。** hindsight 的 8 个性能 issue 每个都附了可复现步骤与 patch 链接；opencode 收到 zsh `q` flag 卡死 shell 扫描器的外部修复（#60791）；pi 收到 Ubuntu 系列 provider 兼容修复（#11781 Azure Foundry 1.05M 上下文、#11785 glm-5.3、#11793 `session-id` 而非 `session_id`）。**上游开始把"如何复现"当成 issue 的必要条件。**
