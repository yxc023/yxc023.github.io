2. **pi 的 chord 在九小时内跨了三个协议版本，且没有发版。** 05:34 宣告 `PROTOCOL_VERSION = 2`（版本不同即以 `protocol-version <n>` 断链），11:55 到 protocol 3，14:29 到 protocol 4；同一天把 `Handle` → `Ref`、`BehaviorOf` → `ImplementationOf`、`kind` → `variant`、`eager` → `lifetime`、`epoch` → code version，`ServeOptions` 变成联合类型且 `ServeOptions.state` 直接消失。**这是一次词汇表重写而非增量演进。** 目前对用户不可见（chord 在 v1.2.0 里被移出依赖、尚未作为发布包对外），但「不兼容即断链」的协议形态已经确定——等它随包发布时，落后的对端不会被降级，只会被关掉。同期落地的 `00d8d04`（reload / retirement 正确性与旧 code generation 的 GC）逐条对着 spec 章节修，说明重写之后紧接着就是对着规范补正确性。

3. **「声明的与生效的不符」这一主题在本期换了三层皮，且全部跨到了部署层。** 上期是 opencode 插件声明 `features.tui: true` 而 TUI 静默跳过；本期是 config schema 是冻结的 V1 文件导致合法的 V2 配置被编辑器标错（#55524）、Windows 默认端口落在 Hyper-V / WinNAT 保留块内导致「注册说在监听而实际没有」（#55547）、hindsight 生成的 skill 在 OpenCode V2 下宣告不可用的工具（#5566）。**元数据先冻结、运行时后演进，是同一个产生问题的机制。**

4. **跨主机与跨信任边界的 context 归属，在两个项目里同一天各出一个问题，方向相反。** pi 侧：远端 Chord 引用接受来自无关主机的 `Ctx` 并执行方法，本地引用却以 `invalid/foreign_ctx` 拒绝（#10959）——**同一契约的校验随部署位置而变**。ACP 侧：#2399 要求接收方忽略未知对象属性（含嵌套 capability 字段）而不放松已知字段校验，#2397 明确「本地 flag 与生成的类型不宣告对端支持」。**前者是在收紧一条漏掉的校验，后者是在明确一条不该收紧的边界——两者都在回答「谁被允许宣称什么」。**

5. **配置优先级正在被当成需要吵一架的设计决策，而不是实现细节。** opencode 在 48 小时内把托管配置从最低（#54921）翻到最高（#55267），并诚实记录了原因不是安全模型而是 **`policies` 按加载顺序反向求值**；pi 的 #10913 则把「精确匹配里没有唯一已认证 provider」从「按 catalog 顺序取」改成报错。两边都在做同一件事：**当配置可能来自多个地方，把「谁赢」显式化，并且说不清时报错而不是随便选。**

6. **本期的缺陷形态高度一致：把一个错误变成一个不再变好的数字，或者变成一句不再生效的声明。** #55389（一条持久化的 notice 让 session 永久 400，且无需用户动作即可触发）、#55367（523k / 524k 个 inotify watch 耗尽后整机 ENOSPC）、#55271（guard abort 了 drain 却不指出是哪一条）、#55290（桌面端静默替换掉配置正确的服务）、#55310（帮助文本说保留 session 数据、实际全删）；hindsight 侧则是 #5565 / #5582 / #5572 / #5574——**「抽取失败」与「抽取为空」在数据上不可区分，「预算」只是一个 prompt 提示而非被强制的上限。** 这一类缺陷不会以崩溃的形式出现，因此也最难在常规测试里被看见。

7. **功能重量继续向桌面端与宿主侧集中，agent loop 本身被当作已定。** opencode v2.0.29 的四个 headline 全部是 desktop（设备配对、provider 账号管理、token 与成本视图、图片缩放平移），TUI 侧唯一新增是把待处理状态上报给终端；第三方追踪文给出的判断同样是「功能重量落在桌面端，而 1.x 线只发布终端界面」。pi-web 15 个新 issue 全在运行时性能与信息架构上；ACP 的增长体现在 client registry 与第三方实现上。**协议与 loop 的不确定性正在被推到宿主与部署形态里去消化。**
