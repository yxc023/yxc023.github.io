- [Session Compaction RFD](https://agentclientprotocol.com/rfds/session-compaction): compactionId 是 agent 自有的不透明字符串，必填、非空、session 内唯一且不复用；`status` 每次 update 都必填，初值 `in_progress` / `completed` / `failed` / `cancelled`，**枚举是开放的**——`_` 前缀留给实现自定义，其他未知值留给未来 ACP 版本，Client 必须原样保留并以通用状态呈现，不得推断生命周期或控制行为。首个 `compaction_update` 固定该实体在时间线上的位置（在先出现的实体之后、后出现的之前），且必须早于任何 `compaction_summary_chunk`；后续 patch 或 chunk 不移动它。
- [Session Notices RFD](https://agentclientprotocol.com/rfds/session-notices): 一条 RFD 里把边界写得很死——notice 没有 ID、没有响应、没有确认、没有更新也没有移除，**SHOULD NOT 进 session replay**；「Agent 必须表现得像这条 notice 可能没被收到、没被理解、没被展示、用户也没看见」。`error` 严重级仍然只是展示事件，不会让 JSON-RPC 请求失败、不停前台工作、不改变会话状态、不隐含 prompt stop reason。如果 Agent 需要知道用户是否看到了 notice，notice 就是错的原语。
- [Migrating from v1](https://agentclientprotocol.com/protocol/v2/migration): 官方 v2 迁移指南把边界写在最前面——「migrating 不等于放弃 v1」，v1-only 的 Agent 与 Client 还会存在相当长时间，应当按连接协商版本、保留 v1、在 feature flag 后面加 v2。v2 里 client 的 fs / terminal 执行 / session modes API 全部移除，agent 需要的客户端侧工具改用 client 提供的 MCP server。
- [claude-agent-acp #1224](https://github.com/agentclientprotocol/claude-agent-acp/issues/1224): 一个真实实现的适配记录，说明 v2 上 compaction 与 notice 的落地差异——v2 客户端过去拿到的是遗留的 "Compact conversation" 工具调用，因为 v2 面没有声明 compaction。适配后 v2 客户端实时会收到 `compaction_update(in_progress)` → `compaction_summary_chunk` → `completed`（失败则 `failed` + 标准 `error`）；replay 时是一条位于摘要原始位置的 completed `compaction_update`。**已知的未解决点**：replay 的 compaction id 与 live 时不同（live 用 Claude Code `compacting` status 的 uuid，transcript 不保留；replay 用摘要消息的 uuid），RFD 与协议都要求稳定 id，要修需要 Claude Code 持久化 live id。
