1. **「一个 `^` 范围引发下游三级事故」是本期最完整的一条因果链**：pi 内部包之间用 `^` 互相依赖 → pi 1.2.0 发布后 `pi-coding-agent@1.0.4` 解析到 `pi-codemode@1.2.0` → pi-web 启动报 `MCP_TYPESCRIPT_PREAMBLE` 导出缺失 → pi-web 06:51 钉精确版本、06:53 发 v0.12.1 → 用户在 03:13 起陆续报三个一模一样的 HTTP 500 → pi 12:28 才在 `f13c00f` 修根因（closes #10865）。**下游比上游早 5 小时 37 分，且两侧各自的补救都被写成了回归测试。** 这是 agent 生态里「第三方包以 CLI 为依赖」这一分发形态的固有暴露面。

2. **agent 产物的生命周期与发布节奏不对齐，同一类洞在三个项目以三种形态出现**：pi #10864——`pi update` 清理旧 release 时不检查运行中的 session，长跑 session 切换到未加载过的 provider 就 `Cannot find module`，且因 `detectInstallChange` 只比对启动时的 `package.json` 而**不给任何重启提示**；opencode #55010——snapshot 仓库把 OpenCode 自己的数据目录录进去，11.5 小时 15 GB，pack 因磁盘满而失败，`failed to pack snapshot objects` 之后主机所有写操作中断；opencode 早期条目 #48657——大未跟踪树下 `git add` 挂起导致 session 永不 drain。三者形状一致：**工具默认「安装物」与「运行物」同步变化，而实际不是。**

3. **「声明的能力」与「实际加载/生效的代码」开始分离**：opencode #55084 里服务端明确报告插件 `active` 且 `features.tui: true`，TUI 却静默跳过其 `./tui` 部分，且同一个包在 `cli.json` 里正常；opencode #55120 的正文写明跨仓库部署序（须等 `opencode-console#3541` 上生产，否则客户端可用旧 trusted client ID + `x-zen-ip` 伪造 IP）；ACP 的 registry 由 bot 一天四次批量刷新，与协议本体零改动同期。协议与扩展生态进入「先声明、后兑现」的阶段，**能力位（capability flag）的可信度正在变成一个新的评测维度**。

4. **hindsight 用 1.0 做了一次「承诺 API、换掉存储」的分工**：开源版继续 Postgres、Enterprise 版换 Rust 的 Memlake，同一套 API 两种后端。支撑这个决定的不是叙事而是三个实测数字（recall 7.0→1.9 qps、190 KB WAL/memory、link 表占库 65% 且四分之三是索引），结论句是「通用关系库每存一次付一次、每查一次再付一次，而一个只增不减的负载意味着永远更大的主库」。同期它在 1.0 tag 前 39 分钟回滚了 #5513——**1.0 的动作既包含对外承诺，也包含对外撤回**。第三方侧的审计稿（solosoft）把「中立基准住在厂商自己的组织里」当作主要论点，说明这类基础设施的评价权已经外移到第三方。

5. **成本与容量从「优化项」升级为「架构分叉点」**：hindsight 那边是「Postgres 到点了 → 换存储引擎」；opencode 这边是同一类调整的客户端形态——chunk timeout 5→15 分钟（#55032，正文点名 DeepSeek 要求至少等 15 分钟）、禁用 Bun fetch idle timeout（#55007）、撞输出上限自动续写（#53876，最多两次、只读最近三条消息）、subagent session 计入展示成本（#55052）。**四条都在承认同一件事：agent 的单次运行时间正在逼近传统客户端的等待假设。**

6. **原生二进制分发与跨架构正确性成为共同战线**：opencode 在 v2.0.28 之内做完 Windows ARM64 的下载、CLI 安装、desktop 更新、免 PowerShell 解包 ripgrep，并加了 `fail releases that bundle native code for the wrong CPU` 的 CI 闸（#54982）；pi-web 在 v0.12.0 里修掉 Windows 命令行在 Node 23–24.19 / 26.6 上以 `0xC0000409`（libuv 断言）退出的问题。**「为错误 CPU 打包」从用户问题变成了构建失败条件。**

7. **ACP 进入静默期，讨论区从「加方法」转向「定责任」**：本期协议本体零改动、新 issue 为零、tag 停在 10-09 的 v1.11.0（release PR #2360 备好 1.12.0 与 v2 alpha.9 未合）。同时讨论区两个活跃议题——#2364 要消息级时间戳（因为 Claude Code 的 transcript 有 `timestamp`、Codex 有 `startedAt`/`durationMs`，而协议没有）、#2299 质疑客户端 filesystem / terminal 能力被收走——都不是在提议新方法，而是在追问「这个信息该由谁提供」。#1237 之后协议侧尚未有新的 RFD 合入。
